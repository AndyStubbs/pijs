# Pi.js 2.3 Sound Upgrade Roadmap

Status: Planned
Design reference: [SOUND-V2.3-PLAN.md](SOUND-V2.3-PLAN.md) (section numbers below refer to it)

## Overview

The work is split into seven phases. Phases 0–4 deliver the core `sound` plugin 2.0.0.
Phase 5 delivers the `sound-advanced` plugin 1.0.0. Phase 6 is the release gate.

```
Phase 0  Foundations ──► Phase 1  Bus & Voice ──► Phase 2  Sound Design
                                                            │
             Phase 4  Music Engine ◄── Phase 3  Samples ◄───┘
                   │
                   ▼
             Phase 5  sound-advanced ──► Phase 6  Release
```

- Phase 3 depends only on Phase 1, so it can run in parallel with Phase 2 if needed.
- Phase 5 can start its `synth.js` work once Phase 2 is complete. The service interface freeze
  follows Phase 4 and validation of the actual advanced-plugin consumers at the end of Phase 5.

### Milestones

| Milestone | Contents | Gate |
| --- | --- | --- |
| M1: Core foundation | Phases 0–1 | Click-free, limited, single-volume synth voices |
| M2: Core complete | Phases 2–4 | All core APIs implemented and tested |
| M3: Advanced plugin | Phase 5 | `sound-advanced` 1.0.0 feature-complete |
| M4: Release | Phase 6 | Pi.js 2.3.0 published |

### Standing rules for every phase

- Each phase ends with `npm test` green and a size report entry (Section 9.1).
- **Listening check:** the relevant demo from Section 10.3 is listened to in Chromium, Firefox,
  and WebKit before the phase closes.
- Commits follow repository conventions: short, imperative, focused on one change.
- `API.md` and the hand-written llms references (`llms.txt`, `llms-full.txt`, `examples.txt`)
  are updated only in Phase 6, to describe final behavior. Plan documents record intermediate
  decisions.
- `docs/llms/pi.d.ts` is generated by every normal `npm run build`, so it cannot wait for
  Phase 6. Commit the regenerated file with each API change, as the existing metadata and type
  tests require.
- Metadata, generated type checks, and signature tests accompany each API change in its phase.
  Phase 6 assembles the final release documentation and declarations.
- Task numbers are sequential within a phase and become GitHub issue titles, so a task added
  later takes the next free number rather than a letter suffix.

Task 0.2 comes first because the type check requires the generated declarations to name
`pi-<majorVersion>`, and the generator takes that name from the highest `metadata/pi-X.Y`
folder. The first API change (task 1.6) needs `metadata/pi-2.3/_removed.toml`, so the bump
must already be in place. After the bump, every normal `npm run build` stamps
`releases/pi-latest` as 2.3.0 from the working tree; that directory is not publishable until
Phase 6, and the frozen `releases/pi-2.2.0` snapshot is untouched.

Exit criteria:

- `package.json` reads 2.3.0 / `"2.3"`, `build/reference-2.3.json` exists beside
  `reference-2.2.json`, and `npm test` passes with the `pi-2.3` declarations.
- The module split passes the existing tests unchanged, and the size delta is at most 0.3 KB
  gzipped.
- The audio browser tests run in Chromium, Firefox, and WebKit from one command, and the
  three-engine listening check has a documented procedure for each engine.
- The harness renders a 2.2 `sound()` call and asserts its peak and length.
- The harness runs a clock-driven test (a 2.2 `play()` string with a mid-song `stopPlay()`) on
  every engine that supports offline `suspend()`. Any engine without it is recorded.
- The masking probe from plan 10.1 passes: a `sound()` call issued from a test action at every
  step of a multi-second render produces one voice per call, the context reports `"running"`
  throughout, and no `statechange` reaches page code.
- Seeded renders are identical across two runs.
- Reference checks accept valid fades and reject abrupt onsets/stops, including sawtooth and
  seeded noise. Numeric tolerances are recorded per metric and engine before Phase 1.
- `npm run size` reports the full-bundle and plugin totals for the 2.2 baseline.
- A baseline size report has been committed to the plan evidence.

Phase 0 results that later phases depend on:

- **D6** is resolved as `provideService()` / `getService()` (plan 4.3 and 12).
- **Engine support** (Playwright 1.56, Windows): Chromium supports offline `suspend()`. Firefox
  renders offline but has no `suspend()`, so its clock-driven tests skip. Playwright's Windows
  WebKit has no Web Audio API, so WebKit runs only the media-element lifecycle tests and its
  listening pass uses Safari. Details are in `test/README.md` and
  `docs/evidence/sound-2.3/README.md`.
- **Tolerances** per metric and engine are in `test/unit/audio-tolerances.js`. Chromium mixes
  multiple inputs in an address-dependent order, so a seeded multi-voice mix is identical only
  within a recorded float tolerance. Single-source seeded renders are bit-identical.
- **Split test loaders:** three Node tests loaded `sound.js` into a `vm` sandbox. They now load
  `samples.js` with a `g_context` stub. Their assertions are unchanged.
- **2.2 parity pin:** `audio-render-browser.test.js` checks that the working tree reproduces the
  recorded 2.2 references. Task 1.6 retires that test with the first `sound()` behavior change.
- **Module layout:** `envelope.js`, `noise.js`, and `scheduler.js` are created by tasks 1.5, 2.1,
  and the first Phase 1 scheduler task, not as empty Phase 0 stubs.

## Phase 1: Bus Safety and Envelope Foundation

Goal: every synthesized voice is click-free, protected from clipping, and controlled by one
master volume.

| # | Task | Plan § |
| --- | --- | --- |
| 1.1 | Build bus graph with effects slots followed by independent output gains | 5 |
| 1.2 | Dedicated bus-volume service method (10 ms ramp; `"master"` shares `setVolume()`); public command ships in `sound-advanced` | 4.3.2 |
| 1.3 | Move `setVolume()` to the master gain only; remove per-voice master gains | 5.1 |
| 1.4 | Two-stage limiter (compressor + soft clipper, knee on a curve sample) with `setSoundLimiter()`; tune compressor against the knee-share metric | 5.2 |
| 1.5 | Implement `envelope.js` (pure math + scheduling) with Node unit tests | 6.2 |
| 1.6 | New `sound()` signature in the ADSR order fixed by D2; remove `attack`/`decay`; stop rounding frequency; validate sweep endpoints; bump the `sound` banner to 2.0.0 with this first breaking change | 6.1, 9.2, 12 |
| 1.7 | `MIN_RAMP` onset floor, `SCHEDULE_LEAD`, and single `stopVoice()` fade path | 6.2, 6.3 |
| 1.8 | Lifecycle states including `retiring`, slot and live-voice caps, and pending records; interim PLAY exemption below | 6.3 |
| 1.9 | Occupancy-interval admission with conflict-time victims; steal overlap, earlier stop deadlines, and completed-ID semantics | 6.3 |
| 1.10 | Hard-cap cleanup order: silent `retiring`, `stopping`, audible `retiring`, unprotected `active` | 6.3 |
| 1.11 | Late requests: expiration before admission, grace, and remaining-envelope onset | 8.1 |
| 1.12 | Autoplay unlock with interruption re-arm; resolve D3 locked-request policy; gesture-synchronous start for deferred requests | 5.3, 12 |
| 1.13 | Remove `webkitAudioContext` fallback | 3 |

Temporary state: `play()` keeps its current emitter and maps its old rates onto the new
envelope until Phase 4. Phase 1 builds a minimal `scheduler.js` for delayed `sound()` requests,
and Phase 4 extends it to `play()`. `<audio>` pools are untouched until Phase 3. Until then,
pool volume follows the master volume through `audio.volume`.

**Interim PLAY exemption.** Until Phase 4, `play()` still creates every note's voice up front,
so a long song would exceed `MAX_LIVE_VOICES` and trigger hard-cap cleanup on its own notes.
During Phases 1–3, voices created by `play()` are excluded from `MAX_LIVE_VOICES` and from
slot admission, and the 2.2 rule for them stays in force: only PLAY voices that have already
started count toward `MAX_VOICES`, and the oldest started one is stopped (now through the
de-clicked `stopVoice()` path) when that count is exceeded. They still use the new envelope,
stop path, and bus routing. Task 4.2 removes the exemption in the same commit that moves
`play()` onto the scheduler.

Exit criteria:

- Every output sample ≤ 1.0 in magnitude on every stress render with the limiter on, and the
  share of samples above the knee meets the target recorded in the plan.
- Stop and onset reference checks pass for `stopSound`, `stopPlay`, voice stealing, and zero
  attack. Future-stop rescheduling preserves continuity and disposes sources exactly once.
- A flood of delayed `sound()` calls stays within `MAX_LIVE_VOICES`, and the pending cap throws
  `TOO_MANY_PENDING_SOUNDS`.
- Overlapping slot holders never exceed `MAX_VOICES` at any instant; all node-holding voices,
  including `retiring`, stay within `MAX_LIVE_VOICES`. Future steals with enough lead fade out
  by the conflict time; immediate and near starts preserve a full victim fade with temporary
  overlap.
- A long sustained voice is not stolen for incoming voices whose conflict set it doesn't
  overlap. An unresolvable multi-victim admission is rejected without touching any victim.
- Forced node-cap cleanup follows the quietest-first order.
- An explicit stop before a future steal fade begins brings silence forward to within
  `SCHEDULE_LEAD + STOP_FADE`. Tests cover repeated earlier stops, scheduled cancellation, and
  forced node-cap cleanup.
- Every immediate automation event lands at or after the scheduling lead: a harness probe
  records the event time requested by the stop, ramp, and rate paths and asserts it is at
  least two quanta ahead of the context time at the call.
- A 2.2-style `play()` string with more than 128 notes plays every note during the interim,
  confirmed by an offline render, and the PLAY exemption is covered by a test that Phase 4
  deletes.
- After a simulated stall, delayed `sound()` requests follow the late-start rule. Rejected and
  skipped IDs accept stop calls as no-ops. Expired requests never allocate nodes or steal slots,
  including requests within the grace interval.
- Envelope stage timing is within 1 ms of the analytic model on all three engines.
- Autoplay unlock is verified manually on desktop and on an iOS or Android device.

## Phase 3: Sample Engine Modernization

Goal: replace `<audio>` pools with decoded buffers and controllable instances.

| # | Task | Plan § |
| --- | --- | --- |
| 3.1 | Decode-mode loading: fetch + decode, retries, single `ready()` wait, abort on remove | 7.2 |
| 3.2 | Stream-mode loading via media element source with `crossOrigin = "anonymous"`; `file:` detection; deferred stream starts run synchronously in the gesture listener | 5.3, 7.2 |
| 3.3 | Sample instances: content budgets, duration-zero handling, fades, and controls | 7.1, 7.3 |
| 3.4 | `stopAudio()` / `pauseAudio()` / `resumeAudio()` by instance, audio ID, or all, following the pause and resume rules in 7.3 | 7.1, 7.3 |
| 3.5 | Position model (lead-aligned rate steps, segment sums, end-time prediction); `setAudio()` in every state, including `pending`, `scheduled`, and paused | 6.3, 7.3 |
| 3.6 | Per-mode `playbackRate` validation (decode 0.0625–16, stream 0.25–4) with `INVALID_PLAYBACK_RATE` | 7.1 |
| 3.7 | Remove `poolSize`, pool terminology, and renamed error codes | 7.1, 11 |
| 3.8 | Rewrite audio lifecycle tests for the new loading model | 10.3 |
| 3.9 | Stream-mode realtime browser test (Chromium and Firefox) with the decode-mode position check | 10.3 |
| 3.10 | `sound_samples_01.html` demo; resolve D5 (iOS audio session) | 10.3, 12 |
| 3.11 | Shared-cap admission, protected loops, delayed loops holding slots from admission, rejected resumes, stream replacement inheriting its slot, completed and never-issued instance IDs | 6.3 |
| 3.12 | Late samples: expiration, advanced offsets, reduced remaining content, onset fade | 8.1 |

Exit criteria:

- In decode mode, offset, content `duration` at rates other than 1, loop wrap, and position
  after rate changes match the position model to the sample.
- Pause and resume honor the saved position and remaining duration. That includes pausing an
  instance before it starts.
- `setAudio()` on `pending`, `scheduled`, and paused instances follows the plan 7.3 table. A
  delayed loop whose rate changed while pending starts late at the position given by its
  recorded segments.
- Out-of-range rates throw `INVALID_PLAYBACK_RATE` in both modes; stream mode is verified
  audible at 0.25 and 4 in Firefox.
- Default duration plays to the end or loops indefinitely. Native duration zero is never used
  for that sentinel; exhausted finite instances do not restart on resume or late admission.
- Stream mode passes the realtime browser test in Chromium and Firefox, its timing tolerance
  is documented in the test, and the decode-mode position check in the same test is within
  tolerance after a rate change.
- A stream instance deferred while the context was locked starts on the unlocking gesture
  without a `NotAllowedError`, verified manually on desktop Safari or iOS.
- Removal, name reuse, and late-event isolation guarantees from 2.2 still hold.
- Samples pass the peak and click checks through the shared bus.
- SFX floods preserve decoded and streamed loops. Protected-only capacity rejects new voices,
  including additional loops, and rejected resumes leave instances paused.
- Delayed loops hold a slot only from admission; explicit stop, pause, and removal release it.
  The 200-request stress case asserts admitted counts and shared caps.
- Replacing a stream loop succeeds while protected loops fill the budget.
- After a simulated stall, surviving samples within grace advance offset and reduce remaining
  content. Beyond grace, only surviving loops start; one-shots complete silently. Expiration
  runs first in both modes. Cover default duration and finite budgets at multiple rates.
- Listening and performance checks validate the initial 64-slot voice budget with mixed
  synth and sample workloads.

## Phase 4: Music Engine

Goal: `play()` uses the new voice path, runs on a lookahead scheduler, and exposes its
extension hooks.

| # | Task | Plan § |
| --- | --- | --- |
| 4.1 | Extend `scheduler.js` to `play()` events; hidden-tab lookahead with capacity-limited window fill (`FILL_HEADROOM`) | 8.1 |
| 4.2 | Convert `play()` emission to the scheduler; route to music bus; remove the Phase 1 interim PLAY exemption and its test | 8.1 |
| 4.3 | `stopPlay()` cancels pending notes and advances active/retiring stop deadlines | 8.1 |
| 4.4 | Tokenizer rewrite: `MA`/`MD`/`MH`/`MR`/`MP`, `WN`/`WP`, `@n`; remove `MT` and aliases; slot, sounding length, gate, and release placement per 8.2 | 8.2 |
| 4.5 | `registerPlayExtension`: registered tokens, duplicate-prefix rejection, per-track state, `copyState` on simultaneous tracks, `resolveNote` at event generation; one-time `@n` warning | 4.3.3, 8.2 |
| 4.6 | Immutable event snapshots; source and insert factories invoked only at admission | 4.3 |
| 4.7 | Tune default PLAY envelope in `sound_play_01.html` | 8.2 |
| 4.8 | Late PLAY: expiration first, grace onset at timeline position, skip beyond grace | 8.1 |

Exit criteria:

- With normal timer delivery, every note is on time and no voice is created outside the window.
- A dense multi-track song in a hidden tab plays without rejected or dropped due notes. Voices
  created beyond the base horizon never push node-holding voices past
  `MAX_LIVE_VOICES − FILL_HEADROOM`.
- After a stall, expired notes complete without admission even within `LATE_GRACE`. Surviving
  notes within grace start with an onset fade at their original envelope position; notes
  beyond grace are skipped. Future timestamps and frozen-context song position are preserved.
- `stopPlay()` mid-song leaves no sound after the fade, including scheduled and retiring voices.
- A stub PLAY extension's state carries across simultaneous tracks, and a queued song is
  unaffected by later changes to that state.
- A long song keeps the node count bounded, confirmed by harness instrumentation.
- Instrumented-song parsing creates no source or insert nodes. Only admitted events invoke
  factories, with fresh instances and snapshots unaffected by later instrument changes.
- A PLAY regression suite of existing sample strings renders the correct notes and timing.
- Under the 8.2 rules, every note's release ends within its own slot, `MS`/`MN`/`ML` shorten
  the sounding portion without changing the beat (a staccato and a legato rendering of the
  same string have the same total length), and a second registration of the `@` prefix
  throws `DUPLICATE_PLAY_TOKEN`.
- No PLAY voice is created outside the scheduler after task 4.2, confirmed by a render of a
  song longer than 128 notes with the interim exemption removed.
- **M2 reached:** the core API is complete, and the core size target is met or a variance is
  recorded.

## Scope-Cut Order

If the schedule slips, features are deferred in this order. Earlier items go first.

1. **Advanced analyser, effects, and periodic noise** move to a 2.3.x plugin release.
2. **Presets and instruments** move to a 2.3.x plugin release. Core `@n` parsing still ships.
3. **The whole `sound-advanced` plugin** ships after 2.3.0 as a standalone plugin release.

Core Phases 0–4 are not cut. If one core item must slip, stream mode is the only candidate. In
that case decode mode becomes the only loading path for 2.3.0, and the `stream` parameter is
held back instead of shipping unimplemented.

## Tracking

- **Progress:** each phase is tracked as a GitHub milestone, with one issue per task number
  (e.g. `Sound 1.6: New sound() signature and ADSR`).
- **Decisions:** closing an open decision updates Section 12 of the plan in the same commit.
- **Size history:** size reports from each phase exit are kept in `docs/evidence/sound-2.3/` so
  the core-merge decision can see the trend.
