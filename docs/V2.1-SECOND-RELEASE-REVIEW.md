# Pi.js 2.1 Second Release Readiness Review

## Outcome

Pi.js 2.1 is **not ready for release**. The build, generated declarations, visual regression
suite, and npm package assembly are healthy, but this review found two release-blocking P1
issues and one P2 version-consistency issue.

The review covered core changes from `v2.0.3` through `HEAD`, with a deeper audit of changes
after the first review at `545dd72`. Pi Vision, unrelated demos, historical generated 2.0.3
artifacts, and other repository-only plugin work were excluded.

## Findings

### FIXED - P1: Removing an offscreen display-shader sampler permanently stalls automatic rendering

Display shaders retain resolved sampler sources in `src/api/postfx.js`. If a retained offscreen
screen is removed, `removeScreen()` deletes its mock canvas from `screenCanvasMap`, but active
display-shader bindings on other screens continue to reference that mock canvas.

On the next presentation, `getWebGL2Texture()` can no longer associate the mock canvas with its
screen. It falls back to passing the plain mock object to `texImage2D()`, which throws a
`TypeError`. The automatic-render microtask does not reset `isRenderScheduled` in a `finally`
block, so the flag remains `true` and subsequent drawing does not schedule another presentation.

Relevant locations:

- `src/api/postfx.js:405-409`
- `src/core/screen-manager.js:556-584`
- `src/renderer/textures.js:128-134`
- `src/renderer/renderer.js:318-329`

Reproduction:

1. Create an onscreen destination and an offscreen source screen.
2. Use the source screen as a persistent `sampler2D` display-shader uniform.
3. Remove the source screen.
4. Draw to the destination and allow automatic presentation to run.
5. Observe `texImage2D` throw `Overload resolution failed`.
6. Draw again and observe that no second presentation attempt occurs.

Recommended correction:

- Track or discover display-shader bindings that depend on a screen being removed.
- Clear or safely invalidate those bindings before deleting the screen mapping and GPU resources.
- Reset `isRenderScheduled` in a `finally` block around automatic flushing and presentation.
- Add a regression test for removing an offscreen screen used by an active display shader.

### P1: The published npm README has unusable installation and quick-start instructions

`releases/pi-latest/README.md` tells users to install and import `pijs`, while the release manifest
publishes the package as `pijs-web`. Its quick-start examples also call:

```javascript
$.screen( "myCanvas", 800, 600 );
```

The current API treats the first argument as an aspect string, so this example throws
`INVALID_ASPECT`. The README is included in the npm tarball and would prevent users from
successfully following the primary installation path.

Relevant locations:

- `releases/pi-latest/README.md:12`
- `releases/pi-latest/README.md:22-25`
- `releases/pi-latest/README.md:37-39`
- `releases/pi-latest/package.json:2`

Recommended correction:

- Change installation and import examples to use `pijs-web`.
- Replace obsolete `screen()` calls with a valid 2.1 aspect/container example.
- Update the README's “What's New” section from 2.0.0 to 2.1.0.
- Re-run `npm pack --dry-run` and inspect the included README.

### FIXED - P2: Root package version metadata is inconsistent

The root `package.json` identifies the project as 2.1.0, while `package-lock.json` identifies both
the lockfile and root package entry as 2.0.3. This does not affect the staged `pijs-web` tarball,
but it leaves the source release and tag internally inconsistent.

Relevant locations:

- `package.json:3`
- `package-lock.json:3`
- `package-lock.json:9`

Recommended correction: regenerate or update the lockfile so both version fields are 2.1.0
before creating the release tag.

## Previous Review Checklist

- **Fixed:** Invalid shader compilation now fails synchronously before a pass is queued.
- **Fixed:** Compiled shader stages and failed programs are cleaned up in `finally`.
- **Fixed:** Removing an image flushes queued texture users before deleting the texture.
- **Fixed:** Generated TypeScript return types and the `screen({ parent })` overload are current.
- **Fixed:** The main README identifies 2.1.0 as the latest version.
- **Fixed:** The reviewed core files pass the whitespace gate.
- **Incomplete:** Automatic render scheduling can still remain stuck after the sampler-removal
  failure described above.

## Validation Results

- Build passed through `node scripts/build.js`.
- Metadata generation and type-definition validation passed.
- Full Chromium core visual suite passed: **34 of 34 tests**.
- Focused shader, view, screen, and image suite passed: **6 of 6 tests**.
- Release staging copied 17 library files and 32 files for four bundled plugins.
- `npm pack --dry-run` passed with 52 package entries.
- All package export targets exist.
- Staged declarations contain the required 2.1 shader lifecycle APIs and return types.
- Full and lite bundles contain the injected 2.1.0 version.
- `git diff --check` passed for the scoped files in both `545dd72..HEAD` and
  `v2.0.3..HEAD`.
- The tracked worktree remained clean during the review; only ignored build, test, release
  staging, and npm-cache artifacts were generated.

The host's user-level `npm` launcher remains broken, so repository scripts were invoked directly
with Node and npm's installed CLI was given a writable task-local cache. This was an environment
issue rather than a Pi.js failure.

## Residual Risks and Coverage Gaps

- No automated test currently removes a screen used by a persistent display-shader sampler.
- The automated visual suite targets Chromium only.
- The suite does not make comprehensive GPU memory assertions.
- WebGL context restoration still does not rebuild renderer resources.

## Release Verdict

**Not ready for release.** Resolve and regression-test both P1 findings before publishing. The
P2 lockfile inconsistency should also be corrected before tagging the release.
